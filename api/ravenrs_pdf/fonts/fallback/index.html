ravenrs_pdf::fonts

Module fallback 

Source
Expand description

The one chain PdfCraft follows when a document does not embed a font program, and a record of what it chose and why.

Substitution used to be decided per caller and never written down: edit picked a craft face by the script of the text it was drawing, Std14::from_base_font matched Latin names, and the renderer did its own thing. Nothing told the user that the glyphs they are looking at are not the ones the document asked for, which is the difference between “PdfCraft shows nothing for my Chinese PDF” being a mystery and being a sentence.

This module answers the dictionary question — “the document does not carry this program; what will stand in for it, and why?” — which is what inspection and reporting need. It deliberately does not answer the text question (“which face has a glyph for こ?”), because that depends on the string being drawn and is already handled where the drawing happens. It delegates to the existing per-script selectors rather than restating their order, so there is one source of truth for each.

The chain is tried in order, and the first step that yields a face wins:

  1. The document embeds the program. Nothing is substituted.
  2. /BaseFont names one of the standard 14 (or a well-known alias such as Arial). Exact published metrics apply, so this is as close to right as a substitution gets.
  3. craft-fonts holds that exact family. Never another family — see crate::fonts::embedding.
  4. The descendant font’s /CIDSystemInfo /Ordering names a script, and craft-fonts has a face for it. Today that means Adobe-Japan1.
  5. The ordering names a script we have no licensed face for (GB1, CNS1, Korea1). There is no honest substitute, so the chain reports none: the caller draws nothing and can say why.
  6. Otherwise, the nearest of the standard 14 by /FontDescriptor /Flags — serif, fixed pitch, bold and italic. This step always succeeds, so a simple font is never left without a face.
